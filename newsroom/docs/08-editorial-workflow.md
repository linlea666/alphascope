# 08 编辑流程、权限与合规

## 1. 新闻事件状态机（Phase 1）

```
detected ─┬→ candidate ─┬→ evaluating → evaluated ─┬→ assigned → covered → archived
          ├→ blocked ───┘  (AI 失败回到 candidate)  └→ declined
          └→ dismissed        candidate → assigned（编辑直接分派）
blocked ↔ candidate（数据恢复或再次过期）   declined / dismissed → candidate（重新打开）
```

转换表在代码（`nr/events/states.py`）和数据库（`event_state_transition`）各一份，测试保证一致；每次转换写 `event_state_history`（谁、何时、原因）。需求中的“待核实 / 已核实 / 事实冲突 / 数据不足 / 发布暂停 / 需要更正 / 已撤稿 / 过期作废”在 Phase 1 分别由这些机制表达：可信度门阻断码（待核实、数据不足、事实冲突）、紧急停止（发布暂停）、更正记录（需要更正）、发布记录撤稿（已撤稿）、归档（过期作废）。Phase 2 把它们提升为显式状态。

## 2. 稿件状态

`drafting → draft_ready → in_review → approved → published → (retracted)`，旁路：`changes_requested`、`stale`（事实变化）、`killed`。

## 3. 权限矩阵

| 浏览事件、故事 | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ | ✓ |
| 请求 AI 评估、手动分派、不报道 | ✓ | ✓ | ✓ | | | | |
| 浏览某账号稿件 | 全部 | 全部 | 授权账号 | 授权账号 | 授权账号 | 授权账号 | 全部 |

## 4. 发布清单（系统自动检查）

记录发布时，以下任何一条不满足都会被拒绝：

1. 稿件状态为 `approved`。
2. 紧急停止未开启。
3. 账号为 `active`，授权状态为 `authorized` 且未过期（每小时还会自动把过期账号改为 `expired`）。
4. 今日（按账号时区）发布数未达到每日上限。
5. 帖子链接属于这个账号（`x.com/<handle>/status/<id>`），发布时间不在未来。
6. 事件门禁仍为通过，且稿件基于当前事实包。
7. 实际发布文本（默认就是稿件正文）重新通过事实守卫。

记录后：稿件变为已发布，分派完成，事件变为已报道，故事章节固定当时的事实包版本，写审计日志。

## 5. 更正与撤稿

- 事实包出现实质变化 → 未发布稿件变为“需重新核验”，必须基于新事实包另存版本才能继续。
- 已发布帖子引用了变化的事实 → 生成更正记录，编辑选择“已确认 / 已更正 / 无需处理”并备注。
- 撤稿：在发布记录里填写原因，稿件变为已撤稿，写审计日志（X 上的删帖或更正帖由运营人员手动完成）。

## 6. 紧急停止

驾驶舱按钮或 `sudo newsroom/start.sh emergency-stop "原因"`：立即拒绝所有发布记录（423）、暂停 AI 任务、取消已排期计划；同步和检测继续运行，以免恢复后丢数据。解除：`resume`。

## 7. X 平台合规要点（Phase 1 的做法）

- 默认人工审核、人工发布；系统不持有任何 X 凭据，不自动发帖。Phase 2 预留的 RPA / API 发布器必须经过同样的授权、紧急停止和审计检查。
- 不自动回复、不批量提及、不组织账号间互动。
- 不把同一篇稿件换词后发到多个账号：同语种近似重复会被守卫拦截；AI 总编辑必须为每个账号给出不同角度或建议沉默。
- 计划参与 X 原创内容奖励的账号：内容由人审核并发布，AI 只是起草工具；是否符合资格以 X 当时的规则为准，系统不承诺资格或收入。
- 账号资料应如实说明是数据研究账号；AI 角色是内部编辑角色，对外不冒充真人记者、交易所或其他机构。
