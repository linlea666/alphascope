# 00 · 数据源可行性与项目评估

> 依据：2026-11-15/16 对 Hyperliquid 公开接口的真实请求与首轮入库结果。凡标注"待验证"的条目都还没有实测。

## 1. 结论先行

**值得做，但必须做成"随时间积累的研究系统"，而不是"一次性把 4.8 万钱包分析完"。**

| 问题 | 结论 |
|---|---|
| 公开数据能否支撑可信的交易员研究？ | 能，但历史深度有限。最有价值的是 `portfolio`（开户以来、剔除资金流的 PnL 曲线）和 `userFillsByTime`（最近约 1 万+ 条成交）。 |
| 4.8 万钱包都值得分析吗？ | 不值得。约 39% 是微尘/零净值账户，60% 近 30 天没有交易。可研究的活跃钱包约 **1.4 万**，值得深度重建的约 **2–3 千**。 |
| 90D / 180D / 365D 指标能算吗？ | 官方排行榜没有这些窗口。可以从 portfolio allTime 曲线算出**粗粒度**版本（点间隔 2–14 天）；逐笔级别的长窗口需要 S3 历史回填或自己积累。 |
| 成本高吗？ | 基础设施不高（P0–P1 约 $40–120/月）。主要成本是研发时间和**等待数据积累的时间**。 |
| 能达到预期吗？ | "去噪排行榜、风险调整评分、潜力发现、可复制性评估"可以达到；"已验证小资金成长""宏观趋势判断""事件前异常"受历史深度限制，只能对部分钱包给出结论，其余标注"证据不足"。 |
| 长期壁垒是什么？ | **时间**：从现在开始积累的排行榜快照、portfolio 快照、成交、前瞻影子跟单结果。这些数据之后再想补，花钱也买不回来。 |

## 2. 官方排行榜 `stats-data.hyperliquid.xyz/Mainnet/leaderboard`

**实测格式**
- 单个 JSON 文件，约 39 MB，由 S3 + CloudFront 提供，下载约 15–17 秒。
- 响应头有 `ETag` 和 `Last-Modified`，支持条件请求：内容没变时返回 304，不产生下载流量（已在系统中实现并验证）。
- 结构：`{"leaderboardRows": [{ethAddress, accountValue, displayName, prize, windowPerformances}]}`
- `windowPerformances` 只有 4 个窗口：`day`、`week`、`month`、`allTime`，每个窗口含 `pnl`、`roi`、`vlm`（字符串数字）。
- **没有 90D/180D/365D**，ROI 的计算口径官方未公开。

**实测分布（47,724 行）**

| 指标 | 数量 |
|---|---|
| 地址重复 | 0（全部小写、格式合法） |
| 账户净值 = 0 | 4,090 |
| 账户净值 < $100 | 约 22,000 |
| 净值 ≥ $1k | 22,213 |
| 净值 ≥ $100k | 13,046 |
| 30 天有成交 | 18,838 |
| **30 天有成交且净值 ≥ $1k（B 层）** | **13,998** |
| 任一窗口 ROI > 1000% | 2,418 |
| 小分母 ROI（净值 < $1k 且 \|ROI\| > 100%） | 4,018 |
| 有全历史 PnL 但没有自身成交量 | 2,141 |
| 有 displayName | 1,481 |
| `prize` 非零 | 0 |

**关键发现：排行榜的账户净值把子账户合并在一起。** 例如 `0x85ec…` 在排行榜上显示 $5,700 万，但它自己的 clearinghouse 只有 $1.87 万，50 个子账户合计持有 $3,170 万永续仓位（另有现货）。因此：
- 单地址 API 返回的数据 ≠ 排行榜上的那个"实体"；
- 系统用 `aggregate_account` 标记这种情况（排行榜净值 > 2 × 该地址自身净值）。已增强的 3,854 个钱包中有 264 个（约 7%）带这个标记；最早一批按成交量排序、大账户偏多时这个比例是 18%，说明问题集中在大账户；
- P1 需要通过 `subAccounts` 接口建立主账户/子账户关系，并把子账户成交合并进来。

**增量发现实测**：首次导入约 16 小时后再次拉取，新增 77 个地址、消失 73 个。说明排行榜是动态集合，必须持续快照，才能保留"失败者"、避免幸存者偏差。

## 3. 官方信息接口 `api.hyperliquid.xyz/info`

| 接口 | 权重 | 实测内容 | 支持的功能 | 限制 |
|---|---|---|---|---|
| `portfolio` | 20 | day/week/month/allTime 及永续版本的 `accountValueHistory` + `pnlHistory`。allTime 从首次入金开始 | 资金流调整收益曲线、粗粒度 TWR/MDD、初始资金估计、潜力识别 | allTime 只有约 100 个点；month 约 45–80 个点 |
| `clearinghouseState` | 2 | 当前持仓、杠杆、强平价、保证金 | 实时风险暴露、持仓快照 | 只有当前时点，历史需自己积累 |
| `userFillsByTime` | 20 + 每 20 条 +1 | 每页 2,000 条；字段含 `dir`、`startPosition`、`closedPnl`、`fee`、`oid`、`tid`、`crossed`、`twapId` | 交易生命周期重建、胜率、盈亏比、持仓时间 | 文档写"只能取最近 10,000 条"；实测一个活跃钱包拿到 14,000 条，最早只到约 4 个月前。高频账户只能回溯几天 |
| `userNonFundingLedgerUpdates` | 20 + 每 20 条 +1 | 充值、提现、内部转账、子账户划转、质押 | 精确资金流、起始资金验证 | 需要分页 |
| `userFunding` | 20 + 每 20 条 +1 | 每笔资金费 | 成本归因 | — |
| `historicalOrders` | 20 + 每 20 条 +1 | 最近 2,000 个订单（含 TIF、触发单、TP/SL） | 执行方式识别（挂单/吃单、止损单使用习惯） | 只有最近 2,000 条 |
| `subAccounts` | 20 | 子账户列表及各自 clearinghouse | 实体合并 | — |
| `userRole` | 60 | user / agent / vault / subAccount / missing | 账户类型识别 | 权重高，按需调用 |
| `candleSnapshot` | 20 + 每 60 根 +1 | OHLCV | 市场环境、MAE/MFE、事件研究 | **每个周期只保留最近 5,000 根**（1h ≈ 208 天，1m ≈ 3.5 天），必须从现在开始自己记录 |
| `metaAndAssetCtxs` | 20 | 235 个永续合约、资金费率、OI | 流动性与容量评估 | 只有当前时点 |

**限流**：每 IP 每分钟 1,200 权重（REST）。WebSocket 最多 10 个连接、1,000 个订阅，**用户级订阅最多 10 个不同地址**，所以实时监控大量钱包只能轮询或自建节点。

## 4. 历史归档（S3）

| 位置 | 内容 | 用途 | 状态 |
|---|---|---|---|
| `s3://hl-mainnet-node-data/node_fills_by_block` | 全网成交（按区块） | 超出 API 窗口的历史成交回填、从成交流里发现新钱包 | 覆盖范围、体量、费用**待验证**（P1 专项调研） |
| `s3://hl-mainnet-node-data/misc_events_by_block` | 转账、资金费、质押等非成交事件 | 历史资金流 | 待验证 |
| `s3://hyperliquid-archive/market_data/...` | L2 订单簿快照 | 滑点与容量模型 | 请求方付费，官方声明"可能缺失" |
| `s3://hyperliquid-archive/asset_ctxs/` | 资产上下文 | 资金费率、OI 历史 | 请求方付费 |

S3 上**没有 K 线**，所以行情必须自己记录。

## 5. 功能 × 数据可行性矩阵

| 功能 | 数据来源 | 可行性 | 说明 |
|---|---|---|---|
| 全量钱包库、新钱包发现 | 排行榜 | ✅ 已实现 | — |
| 去噪排行榜 | 排行榜 + 质量标记 | ✅ 已实现 | — |
| 30D 资金流调整 TWR / MDD | portfolio month | ✅ 已实现 | 点间隔约 10–20 小时，可信度通常为"可靠/一般" |
| 90D / 180D / 365D 收益与回撤 | portfolio allTime | ⚠️ 粗粒度 | 已实现并标注为粗粒度；期间回撤不可见 |
| 胜率、盈亏比、持仓时间 | fills | ✅ P1 | 只覆盖 API 窗口内的成交 |
| 起始资金验证（小资金成长） | portfolio allTime + ledger | ⚠️ 部分 | 只有 allTime 曲线和资金流水能覆盖开户时点的钱包才能给"已验证" |
| MAE / MFE | fills + 自建 K 线 | ⚠️ P1 之后 | 取决于自建 K 线开始的时间 |
| 宏观趋势判断、事件研究 | fills + K 线 + 事件库 | ⚠️ P2 | 历史事件只能覆盖 API 窗口；更早的需要 S3 回填 |
| 跟单可复制性 | fills + 订单簿 + 影子跟单 | ⚠️ P2 | 前瞻验证需要数月 |
| 大规模实时监控 | 自建非验证节点 | 💰 P2 | 节点硬件与运维成本待评估 |

## 6. API 预算（单 IP，每天 1,728,000 权重；默认只用 50%）

| 任务 | 估算 | 每日权重 |
|---|---|---|
| B 层 1.4 万钱包 portfolio + clearinghouse，每 7 天一轮 | 2,000 钱包/天 × 22 | 约 44,000 |
| A 层 3,000 钱包成交首轮回填 | 平均 4 页 × 120 | 约 1,440,000（一次性，约 1 天） |
| A 层成交增量 | 3,000 × 1–2 页 | 约 300,000–500,000 |
| K 线记录（30 个主要币种 × 1m/1h） | — | < 50,000 |

结论：单 IP、合规使用即可支撑 P0–P1，不需要多 IP 绕过限流。

## 7. 成本估算

| 项目 | P0–P1 | P2（含实时） |
|---|---|---|
| 服务器（4 vCPU / 16 GB / 100 GB SSD） | $40–80/月 | $80–160/月 |
| Postgres（自建或托管） | 含在上面或 $15–50/月 | $50–150/月 |
| 原始归档（对象存储） | $1–5/月 | $5–20/月 |
| AI 研究报告（按需生成并缓存） | $20–150/月 | 同左 |
| 自建非验证节点 | — | 待评估（硬件需求需按官方最新要求确认） |
| S3 历史回填 | — | 一次性，费用待调研 |
| 研发时间（单人 + AI 辅助） | P0 1–2 周、P1 4–6 周 | P2 6–8 周 |

## 8. 主要风险

| 风险 | 影响 | 应对 |
|---|---|---|
| 排行榜结构变化 | 入库失败 | 严格 Schema 校验，失败时任务标记为 failed，不写入垃圾数据（已实现） |
| API 历史窗口很短 | 高频账户无法重建 | 标注覆盖率；P1 调研 S3 回填 |
| 子账户合并 | 单地址指标与排行榜不一致 | `aggregate_account` 标记（已实现）；P1 合并子账户 |
| 幸存者偏差 | 只研究了当下的赢家 | 保留消失的钱包与全部快照（已实现）；未来从全网成交流中发现钱包 |
| 粗粒度回撤低估风险 | 风险评分偏乐观 | 可信度分级 + 只用于初筛；正式评分用逐笔重建 |
| 过拟合评分 | 规则只对少数明星有效 | 时间序列滚动验证、样本外检验（见 04） |
| 合规与声誉 | 被理解为指控内幕交易 | 只用中性措辞"事件前异常"，不做身份推断（见 05） |
